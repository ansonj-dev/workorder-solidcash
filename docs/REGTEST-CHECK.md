# BCHN regtest acceptance check

Date: 2026-11-19. A portable Bitcoin Cash Node **29.2.0** build is kept under ignored `tooling/` and was verified against the official Windows archive SHA256 `764ad61419a541148bc501ffd187c619eafea3b2e3f9c3a85e8db9550652b599`. It is not installed system-wide. The local BCHN node runs on loopback in an isolated `regtest` datadir with `acceptnonstdtxn=0`.

## Actual node result

`npm run node:workorder-regtest` compiled the current `WorkOrder.sol`, created and funded its current P2SH32 address with 1,000,000 disposable regtest satoshis, and mined the funding transaction. It then built signed spends using keys generated by the local regtest wallet and checked them with BCHN `testmempoolaccept`.

| Case | BCHN result |
| --- | --- |
| Client and maker approve payment to maker | Accepted |
| Client and maker mutually cancel to client | Accepted |
| Mediator resolves a 400,000 / 590,000 sat split | Accepted |
| Approval payout redirected to client | Rejected by covenant output check |
| Wrong approval signer | Rejected by signature check |
| Mediator payout redirected from maker | Rejected by covenant output check |
| Refund before its block-height locktime | Rejected as non-final |
| Refund using a sequence that disables locktime | Rejected by locktime check |
| Refund after the local chain passed the locktime | Accepted |

The full node version, node upgrade status, policy setting, block heights, contract address and script hash, transaction IDs, input size, and each result are recorded in ignored `artifacts/regtest/workorder-node-acceptance.json`. Raw signed review transactions are also ignored under `artifacts/regtest/`. The current checked-in-source proof includes the generated contract address and its redeem-script SHA256 in the report.

`testmempoolaccept` inspected the signed spends but did not submit any settlement to the mempool or broadcast it. The script does send the contract funding transaction and mine blocks, but only to the disposable local regtest node. The keys, wallet file, RPC credentials, blockchain data, node binaries, and transaction artifacts are under ignored `tooling/` or `artifacts/` paths and must not be committed.

## Repeating locally

On Windows, start the ignored local BCHN binary with the ignored regtest datadir and config, then run:

```powershell
npm run node:workorder-regtest
```

The script requires that project’s ignored `tooling/solidcash-regtest-data/bitcoin.conf` and `workorder-test-keys.json` exist. It verifies the RPC chain before it performs wallet calls, and refuses non-regtest RPC. It creates a fresh contract address for each run by setting its refund height relative to the current local tip.

The separate command `npm run node:check -- <signed-regtest-transaction.hex>` remains read-only: it calls only `getblockchaininfo` and `testmempoolaccept`, refuses non-regtest endpoints, and never funds, mines, or broadcasts. Its injected-RPC tests are not a substitute for the actual node run above.

## Limits of this evidence

- This result is for BCHN 29.2.0, this exact local regtest configuration, UTXO set, policy, and recorded tip. It is not a Chipnet or mainnet transaction or a chain-upgrade compatibility claim.
- The BCHN `getblockchaininfo` result reports the May 2027 upgrade as not yet mempool-active on this regtest instance. No May 2027 activation is claimed or required for these transaction checks.
- The checks cover ordinary BCH `approve`, `cancel`, `resolve`, and height-based `refund` paths. They do not demonstrate token funding (which the covenant explicitly rejects), live multi-party wallet operation, or deployment safety.
- Mainnet testing remains a separate, user-reviewed action. No real BCH was used.

This behavior follows the [BCHN `testmempoolaccept` RPC](https://docs.bitcoincashnode.org/doc/json-rpc/testmempoolaccept/) and [official BCHN download page](https://bitcoincashnode.org/en/download/).
